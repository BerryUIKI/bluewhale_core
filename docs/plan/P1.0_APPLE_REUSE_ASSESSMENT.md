## 1. Package facts

- Two library targets: `BerryLedgerCore` (domain) and `BerryLedgerApplication` (use cases), plus two test targets.
- 87 Swift files, about 720 KB, about 11,450 lines.
- Foundation only: no SwiftData, SwiftUI, UIKit, or AppKit imports in the package. It is portable domain logic.
- Domain target: 3,645 lines; application target: 7,803 lines.
- 189 XCTest cases, of which 143 cover v1 scope and 46 cover features excluded from v1 (budgets, recurring plans, savings goals, wishes, subscriptions).
- Identifiers are random `UUID` (v4). The approved R3 model requires UUIDv7, so identifiers are a deliberate change, not a port.
- The SwiftData schema and its V1-V16 migrations live in the application target, outside this package, and are not part of the reuse scope.

## 2. Method and classification

Each module is classified as:

- **Port**: translate the algorithm faithfully into Rust, preserving exact behavior.
- **Reimplement**: write Rust from the approved R3 model and the behavioral rules, using the Apple code only as a reference.
- **Vectors**: reuse the authored test cases/expected values as behavioral contracts.
- **Exclude**: not in v1 or not portable.

Exact arithmetic is ported; entities and orchestration are reimplemented with Rust idioms, UUIDv7, and the new repository traits. Test cases are reusable as vectors under the licensing decision in section 6.

## 4. Behavioral requirements to preserve

These are the rules the Rust implementation and its vectors must preserve.

### 4.1 Money and currency

- `Money` is `Int64` minor units plus a currency; no floating point anywhere.
- Addition and subtraction require the same currency and use checked arithmetic; overflow is an error.
- Currency codes are three uppercase ASCII letters; scale is 0-9.
- The v1 scale policy contains 40 codes: scale 0 for CLP, ISK, JPY, KRW, VND; scale 3 for BHD, JOD, KWD, OMR, TND; scale 2 for the remainder (including CNY, EUR, GBP, USD).
- Parsing accepts a non-negative magnitude only, ASCII digits with at most one dot, no exponent, no separators; excess fractional digits are rejected rather than rounded; overflow is an error.
- Rounding to the nearest minor unit uses half-up (remainder doubled is at least the divisor) for a non-negative dividend; division by zero or a negative dividend is an error.

### 4.2 Exchange rates

- A quote is a positive exact ratio reduced by GCD; parsing accepts up to nine fractional digits and rejects signs, empty fractions, separators, and exponents.
- Conversion accounts for both currencies' scales, uses a full-width intermediate product, and rounds ties away from zero.
- Selection at a date excludes superseded rates, requires `effectiveAt <= date`, and orders by effective date, then manual over provider, then `updatedAt`, then UUID string descending.
- Source and reporting currencies must differ; `updatedAt` and `supersededAt` must not precede creation.

### 4.3 Transactions and balances

- Kinds: opening balance, expense, income, transfer.
- Amount is always positive. Opening balance has no category, destination, or counterparty. Expense and income require a category of the matching kind. Transfer requires a distinct destination account, no category, and no counterparty.
- A cross-currency transfer requires a destination amount; a same-currency transfer's destination amount, if present, must equal the amount.
- At most one active opening balance may exist per account.
- Balance: opening balance and income add to the source account; expense subtracts; transfer subtracts the amount from the source and adds the received amount (destination amount when present) to the destination.
- Soft-deleted transactions are excluded from balances, statistics, and reports and can be restored.

### 4.4 Time, statistics, filters, dashboard, reports

- All day/month/year boundaries use the ledger time zone and the Gregorian calendar.
- Monthly statistics include active income and expense whose `occurredAt` falls in the ledger-time-zone month; transfers, opening balances, and deleted rows are excluded.
- Filters: kind, account (source or destination), category, tag, counterparty, inclusive day range in the ledger time zone, and normalized search text (trim, canonical composition, case/diacritic/width-insensitive). Sort is `occurredAt` descending, `createdAt` descending, UUID string ascending.
- Dashboard: per-account balances in native currency, converted net balance at each transaction date, available currencies, monthly statistics, daily cash flow, and savings as income minus expense.
- Reports: cash flow with category rows, monthly buckets, and period/average modes; category ranking with share in basis points.
- Ledger profile: name trimmed and NFC-normalized, at most 60 characters, no newlines or control characters; emoji is a single grapheme with emoji presentation, at most 16 scalars.

### 4.5 Validation order observed in the use cases

Transaction creation validates, in order: supported kind, ledger settings, tags, counterparty, account references and archive state, category kind, amount text, destination amount, then constructs the transaction and saves it. Update additionally checks existence, deleted state, and immutable opening-balance kind. This order is part of the contract because clients rely on the first reported error.

## 6. Licensing and provenance decision (proposed)

**Context.** BerryUIKI owns both the private Apple application and the public repositories. The public core is Apache-2.0. Translating private code into a public repository is a licensing act even when the same owner controls both; it must be recorded before code is written.

**Proposed decision.**

1. BerryUIKI authorizes reuse of the algorithms, invariants, and test vectors in `Packages/BerryLedgerCore` for the Rust core, under the Apache License 2.0.
2. The Apple application remains closed source and is not modified. Its UI, assets, app services, SwiftData models, and schema migrations are never reused.
3. Every ported module records its provenance in `docs/reference/apple-provenance.md`: source files, the Apple commit, the reuse type (algorithm, vector, or reference), and the reviewer.
4. Ported algorithms are re-expressed in idiomatic Rust with Rust tests; the public repository does not contain verbatim Swift files or Apple-specific comments.
5. If the owner prefers a clean-room boundary instead, only the vectors are reused with provenance and every algorithm is reimplemented from the R3 contract; the module decisions above remain valid in either case.

**Approval.** The owner must approve this decision (or choose the clean-room variant) before P1.2 code is merged. The decision is recorded in ADR 0005.

## 7. Porting notes

- **Money/Currency:** direct translation; `i64` checked operations and a validated `Currency { code: [u8; 3], scale: u8 }`. Keep the 40-code v1 policy as data with a `policy_version`.
- **Parser/rounding:** operate on bytes; use checked multiply/add; keep the "reject excess fraction" policy and the half-up rule.
- **Exchange rate:** use `i128` for the full-width product and division to avoid manual `UInt64` splitting; preserve the tie-away-from-zero threshold and the selection ordering.
- **Entities:** typed UUIDv7 newtypes; strings trimmed and NFC-normalized on construction; archive booleans; timestamps as UTC instants.
- **Calendar:** use a Rust time crate with IANA time zones (ADR pending, evaluate `jiff` first, fall back to `time` plus a tz database). Preserve Gregorian month/day/year intervals and the ledger-time-zone membership rules.
- **Text normalization:** canonical keys need NFC plus locale-independent lowercase; search needs case, diacritic, and width folding. Document the Rust crates used and test CJK width and accented text explicitly.
- **Repository traits:** define them in `core-domain` from R3; do not translate the Swift async protocols literally. Keep the application layer generic over the traits.
- **Ordering:** keep all observed tie-breakers, including UUID string order, because tests and UI rely on deterministic output.
- **Excluded:** SwiftData models, V1-V16 migrations, SwiftUI, app services, budgets/plans/subscriptions/savings/wishes.

## 8. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Silent divergence in rounding or conversion ties | Wrong balances | Port exact algorithms and port the corresponding vectors first |
| Time-zone/calendar differences between Foundation and the Rust crate | Wrong month membership | ADR for the crate; boundary vectors (month end, DST, Asia/Singapore) |
| Unicode normalization differences | Duplicate names or failed search | Explicit normalization tests for NFC, case, diacritics, CJK width |
| Licensing ambiguity | Legal exposure in a public repo | Owner approval and per-module provenance before code |
| Apple schema history is not portable | Data migration confusion | New core starts at schema v1; the Apple app is not migrated by this project |
| Over-copying application code | Framework and shape coupling | Reimplement use cases from R3; only algorithms and vectors are ported |
